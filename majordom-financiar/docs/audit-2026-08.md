## Phase 1 — Collaboration & Claude setup

### F1 — `scripts/check-private-data.sh` cannot be run as documented · **blocking**

Root `CLAUDE.md` prescribes `bash scripts/check-private-data.sh` as an ad-hoc self-check to
run right after editing any tracked doc. The script lives at the repository root
(`life-os/scripts/`), but sessions run from `majordom-financiar/`, where that exact command
exits 127 (`No such file or directory`).

The pre-commit hook resolves it correctly (`exec "$ROOT/scripts/check-private-data.sh"`), so
the *commit gate* works. What has never run is the mid-session self-check — the capability
added on 2026-07-07 specifically to close the gap that the scanner "only ever ran at commit
time, after a leak was already visible mid-session". The gap it was meant to close is still open.

**Fix (small):** document the path as
`bash "$(git rev-parse --show-toplevel)/scripts/check-private-data.sh"`.
**Fix (better):** register it as a Claude Code `PostToolUse` hook on `Edit`/`Write` of `*.md`,
so it is not a command anyone has to remember to type — consistent with this repo's own
"mechanism, not just a warning" principle.

### F2 — The pre-commit hook is not version-controlled · **blocking**

`.git/hooks/pre-commit` enforces three separate rules: the commit-timestamp window, the
`check_provider_wiring.py` AST check (architecture.md rule 29), and the private-data scanner.
It is untracked and lives only in the local `.git` directory, so a fresh clone silently
enforces none of them.

`CLAUDE.md#new-dev-machine-setup` enumerates exactly what does not transfer on a new machine
(git auth, `.env`, Docker, Ollama endpoint, `settings.local.json`, `PLANNING.md`,
`PRIVATE_context.md`) — the hook is not on that list.

**Fix:** track the hook as `scripts/hooks/pre-commit` and install it from `scripts/setup.sh`
(or `git config core.hooksPath scripts/hooks`), then add it to the new-machine checklist.

### F3 — The "no auto-memory" rule is contradicted by the memory that exists · **important**

`CLAUDE.md#collaboration-rules` states: *"No auto-memory: do not save notes to
`~/.claude/projects/.../memory/`. Save feedback and decisions in this file or in
`docs/decisions.md`."*

That directory currently holds 18 memories, of which roughly seven are about this project and
restate rules already in `CLAUDE.md` — architecture, delegation-prompt style, "discuss before
implementing", "simplify upfront", "product decisions go in CLAUDE.md", the deploy pipeline,
the Telegram removal. Their index loads into every session unconditionally, so the duplication
is paid for on every single run, and the two copies can drift independently — the exact failure
mode `.claude/rules/priority-tracking.md` was written to prevent.

**Decision needed (not a technical call):** either honour the rule and delete the
project-specific memories, or drop the rule and let memory carry that content. Both are
defensible; keeping both as they are is the only option that is not.

### F4 — Collaboration rules are duplicated across the two `CLAUDE.md` files · **important**

Root `CLAUDE.md#collaboration-workflow` (~15 lines) is a compressed restatement of
`majordom-financiar/CLAUDE.md#collaboration-rules` (~40 lines). Both cover the
Claude-architect / DeepSeek-engineer split, the Aider-headless default, and the prompt-file
fallback. Both were edited on the same day (2026-08-29) to apply the same correction — which
is precisely the maintenance burden the priority-tracking rule warns about: *"any doc that
duplicates what an issue's own state already says WILL go stale, because nothing forces the two
to update together."*

That principle was applied to issue status and never to the rule files themselves.

**Fix:** the detailed version stays in `majordom-financiar/CLAUDE.md`; the root file keeps one
line pointing to it, the way it already does for architecture and roadmap.

### F5 — The "Task type → what to read" table is duplicated, and has already diverged · **important**

The same routing table exists in `majordom-financiar/CLAUDE.md` and in `docs/INDEX.md`, and
the two no longer match:

- `docs/INDEX.md` has rows for Notifications/Web Push and Vehicle management that `CLAUDE.md` lacks.
- `CLAUDE.md` has an "Account structure / `create_account` → `PRIVATE_context.md`" row that
  `INDEX.md` lacks.

Neither copy is complete, and a session reading only one gets an incomplete answer. Same
failure mode as F4, except here the drift has already happened.

**Fix:** keep the table in `docs/INDEX.md` only (it is the documentation index); `CLAUDE.md`
already tells sessions to start there.

### F6 — `plan-feature`'s "Known gotchas" list only ever grows · **important**

The list is 12 entries and nothing has ever been retired from it. It is read in full on every
`/plan-feature` invocation, and again by the `pre-commit-review` subagent.

Two of the entries are now enforced mechanically by `scripts/check_provider_wiring.py`, which
already runs in the pre-commit hook and which `pre-commit-review` is explicitly told to run
instead of reasoning about by hand — so the prose duplicates a check that cannot be skipped.
Three more entries are incident narrative (#160/#166 on tool-guide bullets, and two from #208)
whose actionable content is one sentence each.

**Fix:** add a retirement policy to the skill — once a gotcha is enforced by a script, a hook,
or a test, its entry shrinks to a one-line pointer at that enforcement. Narrative detail moves
to `docs/sessions/`, which is where "what happened" already belongs.

### F7 — Process gap #1 ("no regression tests, left open by choice") is worth re-deciding · **important**

The original reasoning was that automated regression tests for the documented silent-failure
rules were not worth the overhead for a single-user app, with a lighter mitigation instead
(open a GitHub issue per newly documented gotcha).

What has accumulated since: six silent-failure rules in `architecture.md` (12, 14, 15, 17, 21,
22), and — in the most recent session alone — four consecutive fix commits for bugs found only
by clicking through the running app (`b5ebad9`, `0f3723f`, `305158e`, `9a4fcad`). One of them,
a `GET /accounts` route silently shadowed by an earlier-registered duplicate, is mechanically
detectable in a few lines. There are no test files in the repository; `tests/` holds CSV and
receipt fixtures.

**This is not an argument for coverage.** It is an argument that a handful of targeted checks
over the *gotcha rules specifically* would have caught bugs that live click-through caught late.
The existing precedent is `check_provider_wiring.py`, which did exactly this for one rule and
worked. Re-decide, rather than re-argue.

### F8 — `docs/decisions.md` has outgrown a flat file · **cosmetic**

1051 lines, roughly 60 entries, no index, with an ADR immutability rule that (correctly)
forbids editing entries — so it can only grow. In practice it is scanned, not read.

Its `## Pending decisions (do not implement without explicit decision)` section holds seven
entries and is a hand-maintained status list — the thing `.claude/rules/priority-tracking.md`
says should be a GitHub label instead. At least one entry is stale: "M2.5 goal proposal —
reframed as budget calibration" is described elsewhere as already decided.

**Fix:** add a heading index at the top of the file; move `## Pending decisions` to GitHub
issues under a `pending-decision` label.

### F9 — Root `CLAUDE.md`'s "Current priorities" section has drifted again · **cosmetic**

The section is dated 2026-07-05 (seven weeks before this audit) and still lists #99, #93 and
#138 as "just completed". `.claude/rules/priority-tracking.md` exists in part because *"the root
`CLAUDE.md` 'Current priorities' list [drifted] from reality for weeks"* — the section survived
the rule that was written about it, and has drifted again in the same way.

**Fix:** replace the numbered list with the query it should have been from the start

about packaging vs. new capabilities, and the Sure/portfolio decision status.

### F10 — `.claude/settings.local.json` permission allowlist is unreviewable · **cosmetic**

Around 80 entries, most of them single-use commands preserved from individual past sessions
(specific `curl` URLs, one-off `python3 -c` inspections, hardcoded historical `GIT_AUTHOR_DATE`
values). Several embed local test credentials in the command string. The file is gitignored, so
this is not a leak — but the list is long enough that nobody can review what is actually
allowed, which defeats the point of an allowlist.

**Fix:** the bundled `/fewer-permission-prompts` skill regenerates a prioritized allowlist from
actual transcript usage. Run it, keep the general patterns, drop the one-offs.

### Not a finding

Checked and clean: `.claude/rules/` path-scoping is correctly configured and both rule files
carry real, specific incident reasoning; `pre-commit-review.md` correctly delegates the provider
-wiring check to the script rather than to prose; `task-complete`'s batching and
conditional-review rules are a genuine cost fix, applied for documented reasons.

### Phase 1 summary

The setup's *content* is unusually good — nearly every rule cites the concrete incident that
produced it, which is rarer than it sounds. The problems are structural rather than substantive:

1. Two enforcement mechanisms do not actually run where they are documented to run (F1, F2).
2. Rules are duplicated across files instead of referenced, and the duplicates have already
   diverged twice (F3, F4, F5).
3. Nothing is ever retired — gotcha lists, decision entries and priority sections only grow,
   including entries that a script now enforces (F6, F8, F9).

The single highest-leverage change is F1+F2 together: make the mechanisms actually run, since
both were built correctly and simply are not wired in.

## Phase 2 — Backend Python

### F11 — 9 of 48 registered tools have no entry in the system-prompt tool guide · **blocking**

`plan-feature`'s known-gotcha list states that every tool needs an explicit bullet in
`_build_system_prompt()` (`backend/api/chat.py`), not just schema registration, and records
this as the confirmed root cause of both #160 (tool silently skipped, model hallucinates an
answer instead) and #166 (model emitted raw internal function-call tokens as chat text). The
entry ends: *"Bit twice now — always add the bullet in the same prompt/commit that registers
the tool."*

It is currently biting a third time. Cross-checking the 48 tool names declared in
`backend/tools/registry.py` against the text of `_build_system_prompt()` — matching both the
prefixed and the bare name — nine appear nowhere in it:

```
finance__get_accounts            finance__get_monthly_stats
finance__get_spending_history    finance__get_transactions_by_tag
system__get_backup_status        system__set_notification_time
vehicle__get_vehicle_log         vehicle__list_vehicles
vehicle__set_vehicle_type
```

Open issue #172 — *"Chat: LLM fabricates plausible-looking data instead of calling finance
tools"* — describes exactly the #160 symptom, and two of the nine unlisted tools
(`finance__get_accounts`, `finance__get_monthly_stats`) are among the most likely to be
wanted for the questions that trigger it. This is a strong candidate cause, worth testing
before treating #172 as a prompting problem.

**Fix:** add the nine bullets, then make the check mechanical. The comparison above is ~10
lines of AST/regex and belongs next to `scripts/check_provider_wiring.py` in the pre-commit
hook — the same rule-to-mechanism move that already worked for the provider-wiring gotcha
(and see F6: once mechanized, the prose entry shrinks to a pointer).

### F12 — The `FinanceProvider` abstraction is bypassed by most of the API layer · **blocking**

`docs/decisions.md#financeprovider-abstraction` (2026-06-03) states that the tool registry
calls the `FinanceProvider` interface rather than the Actual Budget client directly, and that
*"switching backends = one env var change (`FINANCE_BACKEND=actual_budget|sure`)"*.
`backend/core/finance/provider.py`'s own module docstring says the caller *"never imports
`ActualBudgetClient` directly."*

In practice there are two parallel access paths:

- **Via `get_provider()`** — 8 files, including `backend/tools/finance/actual_budget.py`,
  `services/notification_service.py`, `api/home.py`, `api/csv_import.py`.
- **Constructing `ActualBudgetClient` directly** — 11 modules under `backend/api/`
  (`accounts.py`, `home.py`, `budget.py`, `transactions.py`, `setup.py`, `close_account.py`,
  `transfer_conversion.py`, `balance_adjustments.py`, `income_sources.py`,
  `vehicle_accounts_internal.py`, `vehicle_log_actions.py`) — plus
  `backend/tools/finance/vehicle.py:18`, which is a *tool*, the exact layer the decision says
  goes through the interface.

`api/home.py` does both, in the same file. The consequence is concrete: switching the finance
backend today would leave eleven API modules still talking to actualpy, so the documented
one-env-var switch does not hold. The 49-method Protocol plus its 49 verbatim pass-throughs
(~460 lines across two files) currently buys portability the codebase does not actually have.

**Decision needed, not a technical call** — the answer depends on whether the Sure migration
is still live. Root `CLAUDE.md` describes it as conditional, gated on a monthly tripwire.
- If Sure is still plausible → route the eleven API modules through `get_provider()` and make
  the abstraction real.
- If it is effectively off → the Protocol is ceremony that costs a three-file edit per method
  and needed a dedicated script (#126) to stay consistent. Collapse it and use the client
  directly.

Either is defensible. The current half-state is the one that costs the most and delivers least.

> **Status: deferred by decision, 2026-08-29.** The Sure question is a product debate in its
> own right, not an audit finding, and is better held with the full picture in view. Revisit
> after Phase 4, together with the consolidated action list. Nothing else in this audit blocks
> on it.

### F13 — `_get_client()` is copy-pasted eight times, byte-identical · **important**

The same four-line constructor appears verbatim in `api/budget.py:28`, `api/accounts.py:51`,
`api/balance_adjustments.py:19`, `api/close_account.py:20`,
`api/vehicle_accounts_internal.py:25`, `api/transfer_conversion.py:19`, `api/home.py:19`,
with a reformatted variant in `api/income_sources.py:26`. `api/transactions.py` does not even
have a helper — it constructs the client inline seven times (lines 92, 159, 255, 296, 316,
343, 358).

`.claude/rules/duplication-prevention.md` says to extract *"at the second occurrence, not
before and not later"*. This is the fifteenth. The rule is correct and was simply never applied
here — most likely because the rule's own examples are about calculation loops in `client.py`,
so this shape did not read as the thing it was warning about.

**Fix:** one `get_client()` in `backend/core/actual_client/` (or a FastAPI dependency), imported
everywhere. Roughly 60 lines removed and one place to change when construction changes.

### F14 — Private helpers from `client.py` are imported across layer boundaries · **important**

Four underscore-private module functions escape `backend/core/actual_client/client.py`:

| Helper | Imported by |
|---|---|
| `_calc_fire` | `api/home.py:11` |
| `_load_fire_model` | `tools/finance/actual_budget.py:1185` |
| `rule_match_prefix` | `api/proposals.py:64`, `tools/finance/actual_budget.py:1499` |
| `_financial_id` | `api/csv_import.py:36` — and re-exported in `actual_client/__init__.py`'s `__all__` |

A private name listed in a package's public `__all__` is a contradiction in itself. Three of
the four are imported inside function bodies rather than at module top level, which is the
usual signature of an import added to dodge a circular dependency — worth confirming, because
if so it is a layering problem wearing a workaround.

**Fix:** decide per helper. Genuinely shared → drop the underscore and move to a small
`core/finance/` module. Genuinely internal → give the client a public method and call that.

### F17 — Broad exception handling is a recurring class, not isolated · **important**

105 `except Exception` handlers across `backend/`. Twelve swallow the exception with no
handling on the following line (`pass` / `continue` / `return None`), four of them clustered in
`tools/finance/actual_budget.py` (lines 106, 125, 137, 150), the rest in `api/receipts.py`
(464, 491), `core/ocr/vision_engine.py:274`, `api/csv_import.py:284`,
`tools/finance/vehicle.py:103`, and `client.py` (264, 404, 3236).

This has been found and fixed before as a one-off at least twice —
`decisions.md#174-code-audit` (*"CSV error-handling leak fixed"*) and commit `091f6c8`
(*"surface account-type update errors instead of swallowing them"*). Fixing individual
instances has not stopped new ones appearing.

**Fix:** not a mass rewrite. Establish the rule that a swallowed exception must log at
`debug` with the reason it is safe to ignore, then apply it to the twelve. The value is that
the next silent failure leaves a trace — this project's documented bug pattern is
overwhelmingly "failed silently", and these are where that happens by construction.

## Phase 3 — Frontend / UI code

### F18 — Three HTTP layers with divergent 401 behaviour, one of them dead code · **blocking**

There are three separate implementations of "call the backend and handle auth":

| Layer | 401 behaviour | Error thrown |
|---|---|---|
| `lib/auth.ts:49` `authFetch()` | `clearAuth()` + redirect | plain `Error('Session expired')` — **no `.status`** |
| `lib/api.ts:27` `request()` | `clearAuth()` + redirect | `ApiError(401)` — module-private class, **not exported** |
| `lib/vehicleValueApi.ts:13` `request()` | *unreachable* | exported `ApiError` |

Three concrete consequences:

1. **`vehicleValueApi.ts:16-20` is dead code.** It calls `authFetch()`, which already throws on
   401 (`auth.ts:63-68`) before it can return — so `if (res.status === 401)` can never be true.
   Every vehicle-API 401 therefore throws a plain `Error`, never the `ApiError` that same file
   exports. `VehicleDetail.tsx:139` narrows on `error instanceof ApiError` — correct for the
   404 case it targets (that one does produce a real `ApiError`), but silently unreachable for 401.
2. **Two unrelated `ApiError` classes.** `api.ts:17` is not exported; `vehicleValueApi.ts:6` is.
   They are structurally identical and mutually `instanceof`-incompatible, so error narrowing
   only works within one file.
3. **`main.tsx:17-21`'s retry predicate reads `(error as {status?: number}).status`** to suppress
   retries on 401. `authFetch`'s plain `Error` has no `.status`, so anything routed through it —
   all vehicle queries, all `Chart.tsx` refetches — falls through to `failureCount < 4` and
   retries for ~15s, then polls every 5s (`refetchInterval`) on an auth failure. In practice the
   redirect usually cuts this short, which is exactly why it has not been noticed; it is a latent
   version of the bug #208 already found once and fixed locally at `VehicleDetail.tsx:71-72`.

**Fix:** one wrapper. `authFetch` becomes the single transport and throws a single exported
`ApiError` carrying `.status`; `api.ts` and `vehicleValueApi.ts` both use it and delete their own
copies. That fixes all three points at once and makes `main.tsx`'s predicate correct by construction.

### F19 — A component bypasses the API layer entirely, contradicting that layer's own contract · **important**

`lib/api.ts`'s module docstring states: *"Components never call `fetch()` directly — they call
functions from this file."*

`components/FuelReceiptCard.tsx:113-125` calls `fetch()` directly with a hand-assembled
`Authorization` header. Because it uses neither wrapper, a 401 there does not clear auth and does
not redirect — it throws a generic error and the user sees a failure message while still appearing
logged in. Same expired session, third distinct behaviour.

**Fix:** route it through the shared wrapper from F18. The "custom endpoint" reason in the comment
(`confirmEndpoint` is dynamic) does not require bypassing the wrapper — the wrapper already takes
an arbitrary path.

### F20 — `Chat.tsx`'s card dispatch is a 350-line nested ternary with 40 copy-pasted handlers · **important**

Lines ~640-1000 render 21 imported card components through a single chained ternary with 27
`msg.role === '...'` branches. Within it, the `onConfirmed` / `onCancelled` handlers are
byte-identical from card to card:

```tsx
onConfirmed={(message) => {
  setMessages(prev => prev.map((m, i) => i === idx ? { role: 'status' as const, content: message } : m))
}}
```

That exact `setMessages` / `map`-by-`idx` block appears **40 times** in the file. Compare
`AccountTransferCard` (721), `BalanceAdjustmentCard` (743) and `TransferConversionCard` (765) —
identical but for the component name and the message field.

This is the largest single concentration of duplication in the codebase, and it is the direct
reason `Chat.tsx` is 1383 lines. It is also `duplication-prevention.md`'s "extract at the second
occurrence" rule again — the fortieth occurrence this time.

**Fix:** two `useCallback` handlers (`replaceWithStatus(idx, message)`, `cancelAt(idx)`) defined
once, plus a lookup table mapping `msg.role` → component. The ternary chain collapses to a few
lines and adding a card stops meaning "edit a 350-line conditional".

### F21 — No shared card shell, and adding a card is a five-file change · **important**

Eight confirmation cards were sampled: `ProposalCard` (154), `ReceiptCard` (287),
`FuelReceiptCard` (448), `CategoryActionCard` (337), `AccountTransferCard` (179),
`VehicleReminderCard` (175), `SetupBalancesCard` (166), `CsvImportCard` (586) — 2332 lines with
no shared base component (`grep` for a `ConfirmationCard` / `CardShell` / `BaseCard` returns
nothing). There are 21 in total.

Adding one card today requires coordinated edits in five places: the component, the ternary in
`Chat.tsx`, `registry.py`'s `TOOLS`, `_PROPOSAL_TOOLS` in `chat.py`, and the tool-guide bullet in
`_build_system_prompt()`. F11 is what happens when the fifth is forgotten — nine times so far.
This is the frontend twin of F12's three-file provider edit, and it has the same root cause: the
seams multiply faster than the mechanisms that keep them aligned.

**Fix:** lower priority than F18-F20 and worth doing incrementally — extract the shell when the
next card is added rather than as a big-bang refactor. The high-value half is the F20 lookup
table, which removes two of the five files from the common case.

  the pattern the rest should follow.

### Phase 3 summary

The frontend has the same shape of problem as the backend, which is itself the finding: seams
that multiply without a mechanism keeping them aligned.

- **F18/F19 are a correctness cluster** — three transports, three different answers to the same
  expired session, one branch that cannot execute. This is the only place in the audit where the
  current behaviour is arguably wrong rather than merely expensive.
- **F20 is the largest duplication in the repository** — 40 identical handlers in one file.
- **F21 explains F11** — five files must move together to add a card, and nothing checks that
  they did.

F18 and F20 are both self-contained, mechanical, and independently verifiable. They are the two
best candidates for delegation in the whole audit.

## Phase 4 — UX / visual design

Reviewed live against the local stack (`ACTUAL_BUDGET_URL=http://actual-budget:5006` — the
fixture environment, verified before starting), at a 507×835 viewport. Screens covered:
Dashboard, Accounts, Transactions, Planned, Majordom (chat), Analytics.

*All amounts below are illustrative substitutes, not values read from the running instance —
the pattern is what matters, and this file is tracked.*

### F22 — Currency formatting is mutually contradictory between screens · **blocking**

The same amount is rendered in two incompatible conventions one tap apart:

| Screen | Rendering | Convention |
|---|---|---|
| Accounts | `€12.345` | `.` = thousands separator, no decimals |
| Transactions | `+€12345.67` | `.` = **decimal** separator, no thousands separator |
| Categories Watchlist | `€0,00` | `,` = decimal separator |
| Chat | `€40.00` | `.` = decimal separator |
| Goals | `€14k`, `~€155k` | abbreviated |

The Accounts and Transactions rows describe the *same account*: the balance shown on Accounts
as `€12.345` appears on Transactions as `+€12345.67`. Under the Transactions convention,
`€12.345` reads as twelve euros and thirty-five cents. Under the Accounts convention,
`€12345.67` is unparseable.

Negative numbers disagree too: Accounts renders `€-235` (sign after the symbol, hyphen), while
Transactions renders `−€500.00` (sign before the symbol, true minus U+2212).

This is the most serious finding in the audit. Everything else in this document costs time or
money; this one makes a finance app ambiguous about amounts, which is the one thing it cannot
be. A user cannot reliably tell whether a figure means one thousand or one euro.

**Fix:** one `formatCurrency(amount, opts)` helper in `frontend/src/lib/`, one locale, one
decision about decimals and abbreviation, used everywhere including the chat's rendered output.
This is a small, self-contained change and should be the first thing fixed out of the whole audit.

### F23 — Every Dashboard load shows false empty states · **blocking**

On load, before data resolves, the Dashboard tells the user they have nothing:

- *Financial Goals* → "Create your first goal" — while three goals exist
- *Latest Transactions* → "No transactions yet." — while transactions exist
- *Expenses Structure* → "No spending recorded this period yet."

The counter-example is on the same screen: *Balance trend* correctly renders
"⟳ Loading historical balance…" and only then shows data. So the right pattern already exists in
the codebase, three widgets simply do not use it — they treat "no data yet" and "no data at all"
as the same state.

The effect is that the first thing the app says on every single open is that the user's records
are empty, which then silently replaces itself. For an app whose whole value proposition is
trustworthy financial state, this is worse than a spinner.

**Fix:** distinguish `isLoading` from `data.length === 0` in the three widgets, following the
Balance trend widget's existing treatment. Small and mechanical.

### F24 — Two of six primary navigation slots carry no unique content · **important**

- **Analytics** is a full-screen placeholder ("Reports — coming soon").
- **Planned** renders the *Financial Goals* card — pixel-identical to the widget already on the
  Dashboard, with nothing else on the screen.

`decisions.md#planned-tab-added` records the move from 5 tabs to 6. What the sixth tab currently
holds is a duplicate of a Dashboard widget, so a third of the primary navigation leads either to
a placeholder or to something the user just saw.

**Decision needed, not a technical call:** either give Planned distinct content (budgeting and
schedules, per its "Goals & budgeting" eyebrow), or fold it back into the Dashboard and drop to
five tabs. Analytics is a roadmap item (#177) and defensible as a stub — but a stub in primary
navigation is a different cost than a stub behind a menu.

### F25 — Developer language leaks into the user-facing UI · **important**

The Analytics placeholder reads: *"Expenses, income, and savings breakdowns are on the roadmap.
Not yet scoped as a real issue."*

"Not yet scoped as a real issue" is issue-tracker vocabulary. A user has no idea what it means,
and it reads as though the app is talking to its own developer. The rest of the copy in the app
is written in plain user-facing language, so this is an outlier rather than a house style.

**Fix:** one sentence, user-facing. The roadmap status belongs in the roadmap.

### F26 — The chat renders the same tool result two different ways · **cosmetic**

Two consecutive answers to the identical question ("Show me my Groceries transactions for July")
came back formatted differently — one with the payee bolded and no date, the next with the date
bolded and a `·`-separated line. Same tool, same data, same session.

The tool returns structured data and the model formats it freely each time. Harmless, but it
undercuts the impression that the numbers come from a system of record rather than from the model.

**Fix:** format transaction lists in the tool's own output rather than leaving presentation to
the model — consistent with `decisions.md#every-proposed-action-needs-verifiable-proof`.

### F27 — Transactions list wastes its densest space on a truncated, non-distinguishing chip · **cosmetic**

Most rows carry a category chip truncated to "Starting Bala…". The truncation cuts exactly the
part that would distinguish one row from another, and the chip repeats identically down the list,
so it consumes the row's most valuable horizontal space to convey nothing. Selection checkboxes
are also permanently visible on every row plus a "Select all" control, so the list is always in
bulk-edit mode even when the user is just reading.

**Fix:** let the chip wrap or drop it when it repeats; reveal checkboxes on entering a selection
mode rather than always.

### Checked and clean

- **Visual language is genuinely consistent** — type scale, card radius, spacing, the dark
  palette and the single accent colour hold across all six screens. The display face used for
  headings and figures is distinctive and applied consistently. This does not read as a
  templated admin dashboard, which is worth saying explicitly.
- **Navigation is stable** — the bottom bar keeps position and active state correctly across all
  screens; the fixed period bar on the Dashboard (from a prior session) works as intended.
- **The screens are legible at a phone-width viewport** — no horizontal scroll, no clipped
  controls, touch targets adequately sized.

### Phase 4 summary

The app looks considered — the visual system is coherent and deliberately styled, and that is the
hard part to retrofit. The problems are in *data presentation*, not aesthetics:

1. **F22 and F23 are both trust bugs.** One makes amounts ambiguous; the other opens every
   session by stating the user has no data. Neither is a design-taste question, both are small
   fixes, and both are more damaging than anything in Phases 1-3 because the user sees them.
2. **F24 is the only genuine design decision** in this phase, and it needs Doru, not a refactor.
3. Everything else is polish.

Notably, both F22 and F23 already have the correct pattern present in the codebase — the Balance
trend widget loads properly, and formatting helpers exist per-screen. As with every earlier phase,
the gap is consistency, not knowledge.

## Found during Phase 4, outside the audit's scope

**An orphaned `majordom-bot` container has been running since 2026-04-10.** It is not defined in
`docker-compose.yml` (which declares four services plus two profiled ones), its source directory
no longer exists in the repository, and Telegram was removed by decision
(`decisions.md#telegram-removed`). Its environment still carries a `TELEGRAM_BOT_TOKEN` and an
allowed-user-ID list, so a deleted integration has been live and polling for roughly four and a
half months, invisible to `docker compose` and to any code review.

Flagged rather than acted on, per the one-task-at-a-time rule. It warrants its own `ops` issue:
stop and remove the container, and revoke the bot token — the token has outlived the code that
used it, which is the part that matters.
