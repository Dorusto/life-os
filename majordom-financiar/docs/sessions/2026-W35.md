## 2026-08-27 — Backup cron fixed (#180) + duplicate-transaction feature (#181) scoped, implemented, audited, live-tested

### Resolved
- **#180 fixed:** daily backup cron (`0 3 * * * scripts/backup.sh >> /var/log/majordom-backup.log`) had been silently failing for 53 days — `/var/log` is `root:syslog`, not writable by the `doru` user the job runs as, so the redirect failed before `backup.sh` ever started, with no error surfaced anywhere. Found while investigating duplicate transactions on the production LXC, at the user's explicit request to back up first. Fixed by pointing the log at `backups/backup.log` (project-writable path) instead; verified writable, and ran a fresh manual backup immediately (`majordom-20260827-195055.tar.gz`, 56M, contents verified via `tar tzf`).
- **Duplicate-transaction investigation:** re-ran `scripts/ab_audit.py dupes` live on production (script copied into the `majordom-api` container). Of the 9 pairs found 2026-08-03 (`scripts/find_dupe_ids.py`), only 3 remain — the rest were already resolved manually. The ~90 "unmatched pending" hits are internal envelope-account transfers with no bank sync, not real duplicates — left alone, confirmed as expected/out of scope.
- **Root cause identified for the 3 remaining duplicates:** #121 (closed) only handles "bank syncs first, receipt scanned after." The reverse order — manual entry first, bank sync lands later — has no check at all: `run_bank_resync_all()` already returns each newly-synced transaction per account but never compares it against anything.
- **#181 scoped and specced** (deliberately distinct from #117/#120, cross-referenced on both): sync-time check for new duplicates going forward, a historical scan grouped by month, a new review screen (opened from Home, not a new tab) with month drill-down, and a per-pair confirm/cancel merge action that copies category/notes from the manual side onto the bank-synced side before deleting the manual one (never a blind delete). Full design: `docs/specs/duplicate-transaction-review.md`. DeepSeek prompt written and saved: `scripts/prompts/deepseek/181_manual-bank-sync-duplicates.md` — not yet run.
- **#182 filed then closed same session — false alarm.** Initially concluded `scripts/check-private-data.sh` didn't exist (`git log --all -- scripts/check-private-data.sh` from `majordom-financiar/` returned nothing). Root cause of the false conclusion: this repo's actual git root is the `life-os/` monorepo, not the `majordom-financiar/` subdirectory — the script and the pre-commit hook both live one level up (`life-os/scripts/check-private-data.sh`, `life-os/.git/hooks/pre-commit`), and searching path/hooks relative to `majordom-financiar/` as if it were its own repo root missed both. Discovered when the real hook fired on the #181 commit attempt below and blocked it — proving the mechanism was working the whole time. Issue closed with a correction comment; lesson: run `git rev-parse --show-toplevel` before concluding a repo-relative mechanism is missing.
- **#181 implemented (DeepSeek) + audited + fixed + live-tested.** DeepSeek's diff matched the prompt's file list exactly. Audit found 2 real bugs before anything was trusted:
  1. `_find_duplicate_candidates` grouped transactions by `abs(int(tx.amount))` — magnitude only, sign discarded — which could match an expense against an unrelated income of equal size in the same account. Fixed to group by the signed cents value.
  2. Both sides of a pair were identified by `Transactions.financial_id`, but 15 of 234 transactions in one fixture account have `financial_id = None` (anything entered directly in the Actual Budget UI rather than via Majordom or a real bank sync never gets one) — `merge_duplicate_transaction`'s lookup could have matched and deleted an arbitrary transaction instead of the intended one. Fixed to key on the row's own `id` (always present) instead; new architecture.md rule 28 documents the gotcha generally, not just for this feature.
  Rebuilt `majordom-api`/`majordom-web` on the local dev stack and live-tested end to end: created a synthetic duplicate pair in the fixture data, confirmed it surfaced correctly in `/home/duplicates/months` and the month-detail endpoint, confirmed a merge (verified directly in the AB DB: manual side tombstoned, bank-synced side untouched), and confirmed Cancel leaves both sides untouched. Also directly exercised `_find_duplicate_candidates`'s `newly_synced_ids` restriction (the sync-time-only code path, which the fixture stack has no real bank-linked account to trigger end to end) by calling it with a real `financial_id` — confirmed it correctly includes the matching pair and excludes others. `find_dupe_ids.py` (the third investigation script, hardcoded to the user's real account names/amounts from the 08-03 investigation) was deleted rather than committed — superseded by `ab_audit.py dupes`, which is generic.
- **The real `check-private-data.sh` pre-commit hook (see #182 correction above) blocked the first commit attempt** — a "License plate" false-positive on an unrelated docstring line about converting cents to a euro amount, matching the script's own documented digit-pair/word/digit false-positive class. Rephrased the wording; the hook's own guidance ("rephrase, don't `--no-verify`") was followed rather than bypassed.

### Lessons
- Verify the actual git root (`git rev-parse --show-toplevel`) before concluding a repo-relative file/hook doesn't exist — the false #182 conclusion came from searching `majordom-financiar/` as if it were its own repo root, when the real root (and the hook/script both) is one level up at `life-os/`.
- `run_bank_resync_all()` already discards exactly the data (`actual.run_bank_sync()`'s return value) that the new duplicate-check needs — worth remembering to check what an existing method already computes and throws away before assuming new data needs a fresh query.
- Chaining several genuinely-related-but-distinct tasks (backup fix → investigation → feature scoping → a second unrelated ops issue) inside one continuous session without checking in between made the session hard to follow — Doru corrected this explicitly; new CLAUDE.md rule under "Collaboration rules" (`One feature at a time`) makes "one task per session" the explicit standard going forward, not just "no parallel work."
- A live smoke test that returns 0 results (e.g. `synced_accounts: 0` because the dev fixture has no bank-linked accounts) can look like a pass while actually never exercising the code path being tested — worth explicitly checking *why* a count is zero before treating a clean response as verification. Caught here by testing `_find_duplicate_candidates`'s sync-restriction logic directly instead of only through the full `/home/sync` endpoint.

### Unresolved
- Whether/when to persist "dismissed" duplicate pairs (so a cancelled pair doesn't resurface on the next scan) — deliberately left open in the spec, not solved for v1.
- #181's Part 1 (sync-time check) was verified at the function level, not through an actual live bank sync (no bank-linked account available in the dev fixture) — worth a final sanity check the next time a real bank sync runs on production, before fully trusting the "Needs attention"-style badge in practice.
