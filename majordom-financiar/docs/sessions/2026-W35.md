- **A CSS bug chased across 3 iterations before the fix was "make it structurally impossible to fail," not "patch the specific case."** A bottom sheet kept clipping/misplacing itself at narrow widths — root cause was `position:absolute` resolving against a *scrolling* ancestor (so a sheet opened after scrolling down rendered above the fold) layered with a separate "floating centered card" CSS variant whose `calc()`/`max-width` math kept producing edge cases. When re-applying an old decision to a new question, check whether the old decision's actual scope covers the new question, not just its general vibe.

## 2026-08-30 (cont'd) — #223 measured and fixed: Dashboard chart lag is Majordom's connection pattern, not Actual Budget

### Resolved
- **#223 closed.** Added temporary wall-clock logging around `_run()` (client.py's single choke point for every AB operation), loaded the Dashboard once on the local fixture-data stack, measured live. One Dashboard render fires ~9 backend calls launched together by the frontend; total wall time to the last one finishing was **~13s**. Root cause, more specific than "no cache": every one of the 62 `ActualBudgetClient` methods opens a brand-new `Actual(...)` connection — full login, validation, full budget re-download+import — with zero reuse across calls, all serialized behind the one process-wide `_actual_lock` (added for a real reason, #142). A queued call pays the full connection cost on top of waiting for the ones ahead of it.
- **Fix 1 (found mid-investigation, kept as its own small win):** actualpy's own `Actual.__enter__()` already calls `download_budget()` — every one of the 62 `with self._get_actual() as actual:` blocks was calling it again explicitly right after, since the beginning of the codebase. Removed all 62 redundant calls via a scripted regex pass, verified `py_compile` + live Dashboard load still showed correct data after. Measured impact was smaller than expected — login + the first download dominate, not this — but it's real dead work removed for free. `architecture.md` rule 2 and `docs/learn/04-actual-budget.md` updated so no one adds it back.
- **Fix 2 (the real fix): a 4-second shared connection, reads only.** Considered a full always-on persistent connection (bigger win, also speeds up writes) and rejected it after arguing it through with Doru — 0 automated tests in this project means a bad state in a long-lived connection would silently affect every financial write, not just Dashboard loading; too much blast radius for the actual problem (a burst of concurrent reads). Landed on: 8 read-only methods used by the Dashboard (`get_accounts`, `get_balance_history`, `get_home_data`, `get_recent_transactions`, `count_uncategorized`, `count_unreconciled`, `get_duplicate_transactions_by_month`, `get_budget_status`) now share one already-logged-in connection for up to 4 seconds via a new `_get_cached_read_actual()` + `_CachedReadHandle` (a thin context manager whose `__exit__` deliberately does *not* close the connection, so it survives past one method call). Implemented as a drop-in `with self._get_actual()` → `with self._get_cached_read_actual()` swap at exactly those 8 call sites — zero indentation changes, zero changes to any of the 33 write (`commit()`) call sites, which keep using `self._get_actual()` directly, fully isolated, exactly as before. Safe without new locking: every caller already runs inside `_run()`'s single-worker executor behind `_actual_lock`, so only one caller is ever inside the cache-check/create logic at a time.
- **Measured after the fix, live:** the 5 cheap queries dropped from ~0.5-0.66s each to ~10-90ms each (6-50x). Dashboard total wall time: ~13s → ~9s. Confirmed data still correct via a live Dashboard screenshot (identical figures to the pre-fix baseline) before and after each rebuild.
- **Remaining ~9s is not this issue's problem** — split into **#227**: (a) `get_budget_status` fires twice per Dashboard load for the identical month/year, only one frontend call site exists, cause not yet found (StrictMode is enabled in `main.tsx` but shouldn't double-invoke in a production Vite build — flagged as the first thing to check, not confirmed as the cause); (b) `get_home_data`/`get_budget_status` each cost ~2.6-3s of real internal compute even with a warm connection — unrelated to connection overhead, likely inefficient per-transaction iteration, needs its own profiling pass.
- **Conclusion for the #222 decision:** confirmed live — it's Majordom's own connection-per-call pattern, not Actual Budget. Any other backend behind the same client design would show the same symptom.

`backend/core/actual_client/client.py`, `docs/architecture.md`, `docs/learn/04-actual-budget.md`, `CLAUDE.md` (majordom-financiar).

### Lessons
- **Removing an obviously-duplicate call and re-measuring before assuming it was the fix caught a wrong initial diagnosis early.** The plan-feature mid-implementation re-verification rule ("if the code reveals something unexpected, stop and re-verify") earned its keep here: the double `download_budget()` call looked like it should explain most of the lag, but re-measuring live after removing it showed almost no change — login + first-download dominate, not that duplicate. ### Lessons
- **A user's own recalled incident ("balances kept going wrong, I fixed it by hand in AB") was the actual signal that a shipped feature had a real correctness bug — not something code review or the original #181 live-testing session had caught.** #181's own live-testing (2026-08-27) explicitly noted the sync-restricted code path couldn't be exercised (no bank-linked fixture account at the time) — the gap this session found lived exactly in that under-tested corner.
- **Reading the vendored library's actual source (`match_transaction`/`reconcile_transaction`/`create_transfer` in `actualpy`) was necessary, not optional** — `docs/learn/08-transfers.md`'s own "How to record a transfer in actualpy" section had a `# API may vary — check actualpy docs` placeholder instead of real detail; the placeholder was accurate about needing to check, just never followed through until this session needed the real answer for a safety-critical fix.
- **Two already-open, already-commented issues (#117, #120) had each independently touched half of this exact pattern without either being connected to #181's actual risk** — worth treating "a related issue's comment describes a suspiciously similar symptom" as a signal to read that issue's full history before scoping a fix, not just cross-reference it after the fact.
- **A relaxed matching condition, requested to widen legitimate detection, can also widen false-positive surface in a way worth stating explicitly rather than silently accepting** — the fork correctly implemented the brief's instruction to drop the `cleared=False` requirement for transfer legs, and correctly flagged the resulting self-pairing edge case, but the deeper precision trade-off (a cleared transfer leg can now theoretically false-match an unrelated cleared transaction) needed a human judgment call about whether the existing confirm-with-proof safety net was sufficient mitigation — recorded in `decisions.md` as an accepted trade-off, not silently shipped.
