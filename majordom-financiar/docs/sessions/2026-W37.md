## 2026-09-11 — #227's compute-cost half fixed and measured; #245's duplicate-fetch half found to be bigger than scoped, deferred

## 2026-09-11 — Correction: the "whole Dashboard remounts" finding above was a testing artifact, not a real bug

### Resolved
- **Retested #245's duplicate-fetch claim properly and it did not reproduce.** The earlier finding in this same session ("*whole* Dashboard query set double-fires... likely a full component remount") came from reading `read_network_requests` across two separate `navigate` calls without clearing the log in between — every request from the first (stuck, pre-perf-fix) page load was still present when the second navigation's requests were read, double-counting the entire set. A clean single navigation with `clear: true` showed exactly one request per endpoint, `budget-period` included.

- Corrected `CLAUDE.md` and the `docs/sessions/INDEX.md` row for the earlier entry today to remove the wrong "likely full component remount" claim, rather than silently rewriting the original entry above — the mistake and its correction both stay visible.

### Lessons
- **`read_network_requests` accumulates across calls on the same tab until explicitly cleared** — always pass `clear: true` (or open a fresh tab) before trusting a request count as "what this one page load actually did," especially after any earlier navigation on the same tab within the same investigation. Not doing this produced a confident-sounding but entirely wrong conclusion that nearly became this session's next open investigation.
- **A live browser finding that contradicts the issue's own original text (#245 assumed one query, this session's first pass claimed the whole page) deserved a second, independent check (the mount/unmount probe) before being reported as settled** — one measurement technique giving a surprising result is a reason to cross-check with a different technique, not to report immediately.

## 2026-09-11 — Sticky page header shipped (audit §5 item #13, page-header half), real min-h-dvh/h-dvh root cause found and fixed app-wide

### Resolved
- **Started narrow, found something bigger mid-implementation**: added `sticky top-0 bg-background/95 backdrop-blur z-40` to the shared `PageHeader.tsx` (used by all 13 pages — one-file fix for the whole app, confirmed via grep before starting). The class applied correctly (verified via computed style: `position: sticky`, `top: 0px`) but had zero visible effect when scrolling Transactions.
- **Root-caused it live, not guessed**: every page's outer wrapper used `min-h-dvh bg-background flex flex-col overflow-y-auto`. `min-h-dvh` is a *minimum* height only, so the div grows taller than the viewport to fit its content instead of clipping — its own `overflow-y-auto` never actually engages (`divScrollHeight === divClientHeight`, `divScrollTop` stuck at 0 the whole time), and the real scroll happens on `document`/`body` instead (`document.scrollingElement.scrollTop` was the value actually changing on scroll, confirmed via a live JS check in the browser). `position: sticky` was relative to a container that structurally never scrolls, so it had no effect despite being correctly applied.
- **Surfaced the expanded scope to Doru before touching more files**: the same exact `min-h-dvh bg-background flex flex-col overflow-y-auto` wrapper string appears in 15 places across 13 pages (grepped first, all byte-identical). Doru chose to fix all of them now — one mechanical `sed` replace (`min-h-dvh` → `h-dvh`, matched on the full class string so the unrelated `min-h-dvh` usage in Vehicle/AccountDetail's "not found" states — no `overflow-y-auto`, not affected by this bug — was correctly left alone).
- Documented as **`architecture.md` rule 42** — a new full-page wrapper combining `overflow-y-auto` with `min-h-dvh` (instead of `h-dvh`) will silently reintroduce this exact bug, with no error and no obvious symptom beyond "sticky doesn't work."
- `tsc --noEmit` clean. Live-verified on 3 pages after rebuild (Transactions, Dashboard, Settings) — header now stays pinned with the backdrop-blur visible against scrolling content underneath, bottom nav/fixed bars unaffected.
- Commented on **#237** (this issue's first bullet, §2.5) — its other bullets (date-grouping/sticky date headers, ISO-vs-formatted date inconsistency, AccountDetail's flat list, mixed locale strings) stay open.
- **Caught and fixed a private-data-scanner false positive before commit**: the new header className put the z-index utility directly ahead of the background-opacity utility, tripping the license-plate regex (same `[A-Z]{1,2}-\d{2,3}-[A-Z]{2,3}` Tailwind-adjacency false positive documented before) — moved the z-index class later in the string so it isn't immediately followed by a short class, verified the scanner passes clean, no visual change (Tailwind doesn't care about class order).

### Files modified
`frontend/src/components/PageHeader.tsx`, `frontend/src/pages/{RecurringReviewPage,AccountDetail,Dashboard,Accounts,DuplicatesReviewPage,Transactions,UnreconciledReviewPage,Planned,VehicleDetail,UncategorizedReviewPage,BudgetRealismReviewPage,Analytics,Settings}.tsx`, `docs/architecture.md` (rule 42).

### Lessons
- **A CSS class applying correctly (confirmed via computed style) is not the same as it having an effect** — `position: sticky` with `top: 0px` looked completely correct in DevTools-equivalent checks; the bug was entirely in the *container's* scroll behavior, several layers away from the property that looked broken. Checking the sticky element's own computed style first (quick, ruled out "did the class even apply") before checking `scrollTop` on the actual scrolling elements (found the real cause) was the right order — cheap check first, not the other way around.
- **`min-h-*` and `h-*` read as nearly interchangeable at a glance but have opposite implications for a container meant to scroll internally** — `min-h` guarantees a floor and lets the box grow past it; `h` caps it, which is what `overflow-y-auto` needs to ever actually trigger. Worth treating any `overflow-y-auto` + `min-h-*` combination as suspect on sight going forward, not just when a bug report names it.
- **The same license-plate-pattern false positive (a short Tailwind class immediately followed by a numeric class immediately followed by another short class) keeps recurring across unrelated sessions** — third documented instance now. The fix (reorder, don't touch the regex) stays cheap each time, but it might be worth a quick look at whether a slightly narrower regex could dodge Tailwind's own naming convention without losing real license-plate detection, next time this comes up a fourth time.
